harness-mem ／ バージョン差分レポート

旧版と今週の更新版で、何がどう変わったのか

harness-mem（= Claude Code と Codex が同じ記憶を共有するための仕組み）の、2026-07-22 から 07-29 の 1 週間で起きた変化をまとめます。

公開版は 0.29.1 から 0.29.3 に上がり、10 日止まっていた配布が復旧しました。ただし効果の本体は「まだ公開していない 16 件の修正」の側にあります。記憶システムの応答は p95 で 14 ミリ秒になり、テストは初めて全件成功しました。
作成日: 2026-07-29 対象: operator（橘） 本レポートは派生物であり正本ではない 関連: Plans.md §159 / §160

やさしく言うと

harness-mem は、あなたが Claude や Codex と話した内容を裏で読み取って記憶に貯める仕組みです。その「裏で動き続けるプログラム」を daemon（= デーモン。常駐プログラム）と呼びます。

先週まで、この daemon は毎分 1 回、数十秒だけ返事ができなくなる状態でした。記憶を引こうとすると失敗することがあったのはこれが原因です。

原因は「1 分ごとに全部のファイルを一気に調べる」処理でした。会話履歴が育って 9GB / 4721 ファイルになり、調べるだけで 10 秒かかるようになっていたのです。壊れていたのではなく、想定した規模を超えたのが実態です。

今週やったのは、この処理を細切れにして、途中で手を止められるようにすることです。結果、返事の遅さは 100 分の 1 以下になりました。

Q. 今、自分の手元は新しくなってる？

なっています。あなたの daemon は main（= 開発の最新）から動いているので、16 件の修正がすべて入っています。

Q. npm から入れた人も同じ？

いいえ。npm（= 配布場所）は 0.29.3 止まりで、応答性の修正 16 件はまだ届いていません。

Q. どれくらい速くなった？

返事が来なかった回数が 240 回中 73 回 → 300 回中 3 回。応答時間は p95（= 遅い方から 5%）で 14 ミリ秒です。

Q. 今すぐ決めることは？

0.29.4 として公開するかどうかだけです。急ぎではなく、後戻りもできます。

01 ／ Current position

いま「版」が 3 つある

ややこしいのは、harness-mem には意味の違う「版」が同時に 3 つ存在することです。まずここを揃えます。

どの版か今の値意味
あなたの daemon main 最新 実際に動いているコード。LocalWork/Code/CC-harness/harness-mem から起動しており、今週の修正 16 件が全部入っている
npm の公開版 0.29.3 他の人が npm install で入れる版。7/26 公開。応答性の修正は含まれていない
GitHub の main 0.29.3 +16 開発の最新。0.29.3 のタグ以降に 16 件の修正が積まれた状態

つまり 「あなたは恩恵を受けているが、npm 経由の利用者はまだ」という状態です。これが唯一の判断事項につながります。

02 ／ Before

旧版で何が起きていたか

daemon は 60 秒ごとに、他ツールの会話履歴を読んで記憶に入れます。旧版ではこの一連がひとかたまりの処理で、途中で手を止める仕組みがありませんでした。

旧版 ── 60 秒ごとの取り込み処理（途中で止められない）

1ファイルを全部調べる

4721 ファイル（Codex）と 1665 ファイル（Claude）の更新時刻を全件確認する。ここだけで 3〜10 秒

▼

2まとめて読み込む

1 ファイルにつき最大 2MB を一度に読む。読んでいる間は他のことができない

▼

3まとめて解析する

読んだ全部を一度に解析する。ここも途中で抜けられない

▼

41 件ずつ保存する

解析した会話を記憶データベースに書き込む

▼

5データベースの掃除

60 秒ごとに書き込みログを本体へ反映する。4.9GB では重い

この 5 段が終わるまで、生存確認（health）にも検索にも返事ができない。実測で毎分 10〜40 秒の無応答が発生していた。

加えて、これとは別に 3 つ壊れていました。

  • 配布が 10 日止まっていた: GitHub には v0.29.2 があるのに、npm は 0.29.1 のまま。公開処理が途中のテストで落ちていた
  • テストが通らなかった: 開発機に Ollama（= 手元で動く言語モデル）があるかどうかで結果が変わる状態だった
  • 状態表示が嘘をついていた: 「実行中の仕事 50 件」と出るが、実際は 2 か月前に取り残された記録だった

03 ／ After

今週の更新版で何を直したか

同じ 5 段を、各段に時間の上限を置いて、境界で手を止められる形に変えました。図の骨格は上と同じです。差分だけ読めます。

更新版 ── 同じ 5 段（各段で中断できる）

1調べるのも 200ms まで

上限に達したら中断。次回は続きから調べるので、後ろのファイルが放置されない

▼

264KB ずつ読む

2MB を一度に読むのをやめ、細切れにする。読むたびに時間を確認できる

▼

3読んだ分だけ解析する

行がぶつ切りになる問題は、解析側が「完全に読めた行まで」を返す仕組みで吸収する

▼

4保存も途中で止まれる

中断した位置を記録し、次回はそこから再開する

▼

5掃除は 5 分ごとに

60 秒 → 300 秒。データベース自身が普段から少しずつ掃除するので安全

どの段でも上限に達したら中断し、次の 60 秒サイクルで続きから再開する。結果、1 回の停止時間が数十秒から数ミリ秒に縮んだ。

あわせて直したもの

直したもの内容
配布の復旧0.29.3 を公開し、10 日止まっていた npm 配布を再開した
テストの安定化開発機に Ollama があるかどうかで結果が変わる依存を切った。Claude Code から実行しても結果が変わらないようにした
停止処理の穴埋めdaemon が止まらないとき、確実に強制終了する経路を 3 つすべてに入れた
状態表示の修正2 か月分溜まった「実行中」の嘘の記録 49 件を起動時に自動回収するようにした
手順書の追加daemon が応答しないときに「待つべきか止めるべきか」を自分で判断できる手順書を追加した

04 ／ Measured

効果（すべて本番環境での実測）

生存確認の窓口に 1 秒ごとに問い合わせ、返事が来るかと、来るまでの時間を測った結果です。

指標旧版更新版読み方
返事が来なかった回数 73 / 240 3 / 300 30% → 1%。残る 3 件は再起動直後の追いつき処理
応答時間 p50（中央値） 測定不能 1 ms ふつうに使っているときの速さ
応答時間 p95 測定不能 14 ms 100 回中、遅い方から 5 番目。ほぼ最悪値
テスト 失敗あり 3295 件 全成功 このプロジェクトで初めて全件成功した
状態表示の「実行中」 50 件（嘘） 0 件（実態） 2 か月分の取り残しを回収した
npm の公開版 0.29.1 0.29.3 10 日止まっていた配布が復旧

「旧版が測定不能」なのは、返事が返ってこない回数が多すぎて統計として意味を持たなかったためです。

05 ／ Decision

唯一の判断事項: 0.29.4 を公開するか

応答性の修正 16 件は main にありますが、npm にはまだ出ていません。あなた自身は main から動かしているので影響はありません。

選択肢内容と結果
A. 今すぐ公開0.29.4 として出す。npm 経由の利用者も応答性の改善を受け取る。公開処理は 7/26 に一度通っているので、同じ手順が使える
B. しばらく寝かせるあなたの環境で数日動かし、問題がないことを確認してから出す。急ぎでないなら妥当
C. §160 まで待つ残っている課題（データベースが大きいと 1 件の保存が遅い）を直してからまとめて出す。ただし §160 は調査から始まるので日数が読めない

公開は tag を打って push するだけですが、その push だけは人の承認が要る設定（本番公開の安全装置）なので、実行するときはあなたの手で 1 コマンド打つ形になります。

判定

今週の更新で、記憶システムの実用上の問題（毎分の無応答）は解消しました。あなたの手元はすでに最新で動いており、追加の作業なしで恩恵を受けています。残る判断は「npm にも出すか、いつ出すか」の 1 点だけで、どれを選んでも後戻りできます。

正直な但し書き

  • 完全にゼロではありません。300 回中 3 回、再起動直後の追いつき処理で返事が遅れます。定常状態では出ません。
  • 根本の下限は残っています。記憶を 1 件保存するコストがデータベースの大きさに比例して増えます。空のデータベースなら 70KB の本文でも 55 ミリ秒ですが、本番の 4.9GB では処理が 11 秒に達することがあります。§160 として起票済みで、まず計測してから対策する順序を明記しています。
  • 原因の特定に 5 回失敗しました。症状から機構を推測するたびに外し、当たったのは毎回「計測する仕組みを入れた回」でした。この教訓は decisions.md に記録しています。
  • 効果の数値は 1 台での実測です。他の環境（会話履歴の量が違う、ディスクが遅い等）で同じ比率になるかは未検証です。

分析方法とデータの制約

  • 応答性の数値は、本番 daemon（port 37888）に curl で 1 秒間隔・240〜300 サンプルの実測。タイムアウトは 5 秒
  • ブロック箇所の特定は macOS の sample（1 ミリ秒間隔でプログラムの実行位置を記録）と、daemon 自身に入れた所要時間ログ（HARNESS_MEM_SLOW_TICK_LOG_MS、既定 1000ms 超過のみ記録）による
  • ファイル数と容量は find と du の実測（2026-07-28 時点）
  • 測定はすべて 1 台（operator の macOS 環境）で行っており、他環境での再現性は未検証
  • 「旧版」の数値は、修正投入前に同一手順で測った値。厳密な A/B ではなく時系列比較である点に注意
