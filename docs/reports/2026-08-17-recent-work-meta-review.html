直近の作業は、結局なにをしていたのか？

harness-mem は、あなたが Claude Code や Codex で作業した内容を手元のデータベースに貯めて、次のセッションで思い出させる仕組みです。直近はその「貯める処理が固まる」不具合を追っていました。

新機能はひとつも作っていません。やっていたのは 自分が出した主張の検証 です。自分の測定報告を 2 回訂正し、同じ形の欠陥の残りを探し、「環境のせい」と曖昧に書いていた不調の正体を突き止めました。
2026-08-17 対象: 2026-08-05 〜 08-07 の作業（§160-005d / 160-006 / 160-007 / S156-FU13 と v0.29.5・v0.29.6） この資料は理解用の派生物であり、正本ではありません

やさしく言うと

harness-mem の常駐プログラム（= パソコンの裏でずっと動いている見張り役。以後「見張り役」）が、履歴を取り込むたびに数十秒フリーズしていました。原因を 5 か所直して公開し、実機で測り直しました。

結果は「大きく改善したが、目標には届いていない」。最悪 173 秒 → 17 秒まで縮みましたが、目標は 0.2 秒なので、まだ 87 倍です。

メタな話として面白いのはここです。この 3 日間で見つかった誤りは 6 件あり、そのすべてを人力の気づきではなく、あらかじめ仕込んでおいた仕組みが捕まえました。仕組みが元を取った 3 日間、というのが直近の実像です。

結局、遅さは直ったの？
日常利用では困りません。応答確認 90 回すべて成功、最大 1.07 秒。ただし見張り役を再起動した直後の 20〜60 分だけ、最大 17 秒固まる区間が残ります。
なんで訂正が 2 回もあるの？
1 回目は測る時間帯を 20 分しか取らず、たまたま静かな時間を拾ったから。2 回目は「いつでも起きる」と書いたが、実際は起動直後に偏っていたから。どちらも追加観測で自分の記述を否定しました。
同じ欠陥が 3 回ってどういうこと？
「定期実行と手動実行が同じ関数を共有していて、手動実行まで打ち切られる」という同型の欠陥が、取り込み経路 3 つに独立して存在しました。1 か所直して終わりにしていたら残り 2 つは生き残っていました。
立花が判断すべきことは？
2 つです。(1) 残り 2 タスクのどちらを先にやるか。(2) 今回得た教訓 3 件を SSOT（= 正本の判断記録）へ昇格させるか。詳細は最後の節にあります。

Meta  /  03

どの仕組みが、どの誤りを捕まえたか

ここが本題です。誤り 6 件を並べても反省文にしかなりません。大事なのは それぞれを何が捕まえたか です。捕まえた側は、すべて事前に用意してあった仕組みでした。

  • タスクの完了条件 (b)「未達を達成扱いにしない」 が、92.5 倍という過大報告を捕まえた。
    何が起きたか

    cd3e059 → 35ab9b2

    更新直後の 20 分だけログを見て「17 万ミリ秒 → 1,875 ミリ秒、92.5 倍」と報告しました。その窓は偶然静かな時間帯で、代表性がありませんでした。再起動以降の全区間で取り直すと最大 17,384 ミリ秒。完了条件に「収まらない場合は収まらなかったと数値付きで記録する」と先に書いてあったので、都合の良い数字で閉じられませんでした。

  • 追加の時間分布観測 が、「停止はいつでも起きる」という自分の記述を捕まえた。
    何が起きたか

    7c715bd

    「停止はログ全域に散在し、起動直後固有ではない」と書きました。稼働 19 時間目に 40 分の窓で測り直すと、codex 経路 0 件 / cursor 経路 0 件。バーストは再起動後 20〜60 分に偏っていました。区間の内部では散在していたが、区間そのものは時間的に有界だった、が正しい記述です。

    この訂正には副産物がありました。「再起動直後だけ重い」という形は、走査位置がメモリ上にしか無く（new Map()）再起動で 0 に戻る、という仮説をよく説明します。誤りを直したら、次の一手の見当がついた例です。

  • レビュー が、自分が新しく入れた不具合を捕まえた。
    何が起きたか

    予算の仕組みを入れるとき、定期実行の登録先を間違えて、利用者が明示的に呼ぶ取り込み API を登録してしまいました。結果、手動で「全部取り込め」と命じても 0.2 秒で打ち切られる状態になりました。仕様書には「明示的な取り込みは予算の対象外、完走してよい」と書いてあり、それに反していました。レビューが重大として指摘し、定期実行用と手動用を分離しました。

  • CI（全テストの自動実行） が、手元で見落とした壊れたテストを捕まえた。
    何が起きたか

    手元では関係しそうな 2 ファイルだけ実行して先に進めました。CI が全体を回して失敗を出しました。以降は送る前に全テストを回すようにしました。部分実行は「通った」の根拠にならない、という当たり前の話が実際に効いた場面です。

  • 曖昧語で止めなかったこと が、「環境負荷」と書いていた不調の正体を捕まえた。
    何が起きたか

    f3ec8dd（160-009 として起票）

    「全テストを回すと毎回違うテストが時間切れになるが、単独では通る」という現象が続いていました。作業中は「環境負荷」と曖昧に記録していました。実体は、見張り役を止めるたびに検索用の子プロセスが 1 個ずつ残り、親を失った状態で CPU を 1 コア占め続けていたことでした。実測で 5 個、合計 628 時間ぶんの CPU。4 個止めた時点で負荷指標が 8.02 → 4.93 に落ちました。

    これは「曖昧に書いたこと自体」が問題だった例です。「環境のせい」は原因ではなく、調べていないという状態の名前でした。

  • S156-FU13 の再検証 が、1 か月前の受け入れ根拠の循環を捕まえた。
    何が起きたか

    docs/benchmarks/bilingual-baseline-2026-08-05.md

    2026-07-07 に日英混在ベンチの合格ラインを 0.86 → 0.82 に下げました。その根拠として「別の独立した指標が 0.90 で緑だから問題ない」と書いてありました。調べると、その 0.90 は同じ測定であり、しかも 2026-05-27 から更新されていない古い値でした。独立した裏付けではなく、自分自身でした。

    0.82 という値そのものは、本当に独立した別の合格ラインで支えられているので変わりません。訂正したのは根拠の書き方です。

  • 本番データベースの中身は読んでいません。読んだのはログとファイルサイズだけです。
