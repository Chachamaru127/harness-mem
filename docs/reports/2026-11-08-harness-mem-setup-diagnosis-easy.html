テストが通っていない変更でも、本体に入れられる状態だった

harness-mem を RouteCLI の運用につなぐ前の診断。2026-11-08 時点、commit 21253878。まだ何も変更していない。

いまの harness-mem は、自動テストの結果を待たずに変更を main（本体）へ取り込めます。門番がいないためです。

門番を置けば止められることを、機械の全探索で確かめました（違反 0）。GitHub の設定を変えるかどうかは、あなたの判断です。

何が起きるのか

ふだんの流れはこうです。変更を書く、PR（変更の提案）を出す、自動テストが走る、問題なければ本体に取り込む。

変更を書く手元の作業
→
PR を出す提案の場
→
自動テストtest-suite
→
main へ取り込む本体
→
公開tag で npm へ
いまはここが通れる自動テストの結果が「実行中」でも「失敗」でも、main へ取り込める。止める設定が入っていない。

実際に模型が出した筋書きは 3 手でした。計画 → PR → 取り込み。テストはまだ走っている途中です。

困るのは、壊れた変更が本体に入ってしまうことです。あとで気づくと、どの変更が原因かを探す手間が増えます。この repo の workflow のコメントには、以前「リリース直前にテスト失敗が初めて分かった」という記録が残っています。

なぜそうなっているのか

GitHub には「このチェックが通らないと取り込みできない」という設定があります。いまの main にはその設定がありません。確認コマンドは 404 Branch not protected を返しました。

テスト自体は PR ごとに走っています。走っているのに、止める力がない状態です。警報機は鳴るけれど、ドアに鍵が付いていないのに近いです。実際には、test-suite.yml は PR と main への push で実行されますが、取り込みの条件にはなっていません。

どう確かめたのか

  1. 仕様書（Spec.md）と開発の約束（AGENTS.md）、2 つの workflow から、「PR を出してから公開するまで」の流れを小さな状態模型にしました。
  2. 機械が取り得る順番を全部試します（全探索）。人が思いつかない順番も出ます。
  3. 3 つの問いを検査しました。
検査問い結果
C1 main に入る変更は、その同じ変更のテストが緑か 反例あり
TLC 終了 12、17 状態を生成し 9 状態を到達
C2 公開まで到達できるか（正常な道が塞がっていないか） 到達できる
TLC 終了 12 を到達経路として確認、65 生成 / 25 到達
C3 門番を置いたら C1 は止まるか 違反なし
TLC 終了 0、51 生成 / 17 到達

この検査が言える範囲。言えるのは「作った模型の中では、この順番で取り込める」ことです。実際の GitHub で取り込みを試したわけではありません。保護設定が無いことは実測（404）です。模型と実物の対応は、仕様書と workflow の記述に基づきます。
